Declarative Diagrams es una herramienta open source para crear diagramas escribiéndolos en YAML. Con ese texto genera un SVG interactivo, un PNG o un componente `<Diagram />` para sitios MDX/React. Su uso principal es dibujar arquitecturas de AWS y Azure con sus iconos oficiales, aunque también sirve para diagramas de flujo y con un estilo visual propio. Ese estilo propio es el que uso para los diagramas interactivos de mi blog. Incluye además un servidor MCP, una skill y un agente para que un asistente de IA pueda crear un diagrama, verlo renderizado y corregirlo.

## Por qué construí Declarative Diagrams

Hace un tiempo me encontré con el mismo problema una y otra vez. Diseño soluciones de arquitectura para mis proyectos y necesitaba tres cosas: diagramas de arquitectura en AWS y Azure, que es lo que los equipos reconocen de inmediato; diagramas de flujo; y un estilo visual propio, tanto para los entregables de clientes como para los diagramas interactivos que quería publicar en mi blog. Ninguna herramienta que probé cubría todo bien. Y cada cambio significaba abrir una aplicación visual, mover cajas a mano, exportar y pegar la imagen en la documentación. Al final, el diagrama quedaba desactualizado.

Así nació *Declarative Diagrams*. La idea es sencilla: si un diagrama es un archivo de texto, puedo versionarlo, revisarlo en un pull request, validarlo y renderizarlo donde haga falta. Y, de paso, un asistente de IA puede escribirlo y corregirlo.

## Como se ve crear un diagrama en "**Declarative Diagrams**"

Un diagrama de arquitectura con estilo AWS se escribe así:

```yml
    nodes:

```

</CodeBlock>

Y con la CLI, dgm, se valida y se renderiza:

<CodeBlock title="terminal" lang="powershell" maxHeight="16rem">
```powershell
dgm validate examples/aws-genai-chatbot.diagram.yaml                                          # errores y advertencias, con sugerencias
dgmrender examples/aws-genai-chatbot.diagram.yaml -o examples/out/aws-genai-chatbot.svg       # SVG interactivo
dgm render examples/aws-genai-chatbot.diagram.yaml -o examples/out/aws-genai-chatbot.png
```
</CodeBlock>

## Un estilo propio para mis diagramas interactivos

Aquí está la parte que más me ilusiona. Quería que los diagramas de mi blog se vieran como mi blog: los mismos colores, la misma tipografía y el mismo modo claro u oscuro. Y quería que fueran interactivos, no una imagen plana.

Para eso, cada tema se define con un color semilla y el resto de la paleta se genera automáticamente, con verificación de contraste para que el texto siempre se lea. Un tema se escribe en un archivo YAML pequeño:

<CodeBlock title="Definición de un tema" lang="yml" maxHeight="20rem">
  ```yml
  name: mi-blog
  extends: distill
  seed: { accent: "#5f6f1f", flow: "#c98a1b", neutral: "#f1f0e4" }
  dark:  { accent: "#a9bb62" }
  ```
</CodeBlock>

Con eso, un diagrama se incrusta en un post MDX con una línea:

<CodeBlock title="Incrustación en Astro / React" lang="TypeScript" maxHeight="28rem">
    ```typescript
    import arch from "./arquitectura.diagram.yaml";
    import { Diagram } from "@declarative-diagrams/react";
    
    <Diagram client:visible svg={arch} caption="Figura 1. Arquitectura de referencia." />
    ```
</CodeBlock>

El diagrama sigue el modo del sitio, y el resaltado, el flujo animado y el revelado paso a paso funcionan dentro del post. Para un artículo técnico, eso permite explicar un flujo sin pedirle al lector que imagine nada.

Además, incluí siete temas base (`distill`, `olive`, `azure`, `aws`, `orange`, `slate`, `mono`), así que puedo empezar desde uno y ajustar.

## Cómo está hecho por dentro
Es un monorepo de npm workspaces en TypeScript. Cada paquete tiene una responsabilidad:

| Paquete | Qué hace |
| :--- | :--- |
| **`core`** | La especificación (validada con Zod), el layout con ELK, el render a SVG, los temas, los iconos y la exportación a PNG |
| **`cli`** | La herramienta `dgm` |
| **`react`** | El componente `<Diagram />` y un plugin de Vite para MDX |
| **`mcp`** | El servidor MCP para agentes de IA |
| **`skills/diagram-author`** | La skill con el flujo de trabajo y los patrones de AWS y Azure |
| **`site-demo`** | Un sitio Astro que aloja el playground |

## Iconos
Los de Lucide (más de 2.400) vienen incluidos. Los de Azure y AWS no los distribuyo: cada usuario descarga los paquetes de los sitios oficiales y los importa con dgm icons update. No quería redistribuir activos de terceros, y el proyecto está pensado así desde el principio.

## Listo ser asistido por IA
El servidor MCP expone herramientas como `dgm_search_icons`, `dgm_validate_diagram` y `dgm_render_diagram`. El asistente consulta la guía, busca los iconos (sin inventarlos), escribe la especificación, la valida, renderiza un PNG, lo mira, corrige y lo guarda.

Ese último paso, mirar el resultado, es el que importa. Un modelo que escribe YAML a ciegas comete errores de layout que no ve. Con el PNG delante, los corrige. Hay además un agente para `OpenCode (diagram-specialist)` que encapsula todo el proceso y acepta texto, archivos del proyecto o una imagen de referencia, como una captura del portal o un boceto a mano.

## Seguridad

Cuando un asistente escribe archivos, hay que tratar el contenido con cuidado. El proyecto tiene un modelo de seguridad explícito: los valores de tema se validan antes de entrar en el SVG, los iconos pasan por una lista blanca que bloquea scripts y enlaces externos, y el servidor MCP solo escribe dentro de la raíz del proyecto sin reemplazar archivos existentes. El SVG interactivo incluye un pequeño script, así que si lo sirves en tu web, hazlo desde tu propio origen, o usa `--static` si necesitas un archivo sin scripts.
