Declarative Diagrams is an open-source tool for creating diagrams by writing them in YAML. From that text it generates an interactive SVG, a PNG, or a `<Diagram />` component for MDX/React sites. Its main use is drawing AWS and Azure architectures with their official icons, although it also works for flow diagrams and has a visual style of its own. That custom style is the one I use for the interactive diagrams on my blog. It also includes an MCP server, a skill, and an agent, so that an AI assistant can create a diagram, see it rendered, and fix it.

## Why I built Declarative Diagrams

A while ago I kept running into the same problem. I design architecture solutions for my projects, and I needed three things: AWS and Azure architecture diagrams, which is what teams recognize at a glance; flow diagrams; and a visual style of my own, both for client deliverables and for the interactive diagrams I wanted to publish on my blog. None of the tools I tried covered all of this well. And every change meant opening a visual application, moving boxes by hand, exporting, and pasting the image into the documentation. In the end, the diagram was always out of date.

That is how *Declarative Diagrams* was born. The idea is simple: if a diagram is a text file, I can version it, review it in a pull request, validate it, and render it wherever it is needed. And, along the way, an AI assistant can write it and fix it.

</CodeBlock>

With the `dgm` CLI, you validate and render it:

<CodeBlock title="terminal" lang="powershell" maxHeight="16rem">
```powershell
dgm validate examples/aws-genai-chatbot.diagram.yaml                                          # errors and warnings, with suggestions
dgm render examples/aws-genai-chatbot.diagram.yaml -o examples/out/aws-genai-chatbot.svg       # interactive SVG
dgm render examples/aws-genai-chatbot.diagram.yaml -o examples/out/aws-genai-chatbot.png
```
</CodeBlock>

## A custom style for my interactive diagrams

This is the part I am most excited about. I wanted the diagrams on my blog to look like my blog: the same colors, the same typography, and the same light or dark mode. And I wanted them to be interactive, not a flat image.

To achieve that, each theme is defined with a seed color, and the rest of the palette is generated automatically, with contrast checks so the text is always readable. A theme is written in a small YAML file:

<CodeBlock title="Theme definition" lang="yml" maxHeight="20rem">
  ```yml
  name: my-blog
  extends: distill
  seed: { accent: "#5f6f1f", flow: "#c98a1b", neutral: "#f1f0e4" }
  dark:  { accent: "#a9bb62" }
  ```
</CodeBlock>

With that, a diagram is embedded in an MDX post in a single line:

<CodeBlock title="Embedding in Astro / React" lang="TypeScript" maxHeight="28rem">
    ```typescript
    import arch from "./architecture.diagram.yaml";
    import { Diagram } from "@declarative-diagrams/react";
    
    <Diagram client:visible svg={arch} caption="Figure 1. Reference architecture." />
    ```
</CodeBlock>

The diagram follows the site's mode, and the highlighting, the animated flow, and the step-by-step reveal all work inside the post. For a technical article, this makes it possible to explain a flow without asking the reader to imagine anything.

I also included seven base themes (`distill`, `olive`, `azure`, `aws`, `orange`, `slate`, `mono`), so I can start from one and adjust it.

## How it works inside

It is an npm workspaces monorepo written in TypeScript. Each package has a single responsibility:

| Package | What it does |
| :--- | :--- |
| **`core`** | The specification (validated with Zod), the layout with ELK, the SVG rendering, the themes, the icons, and the PNG export |
| **`cli`** | The `dgm` tool |
| **`react`** | The `<Diagram />` component and a Vite plugin for MDX |
| **`mcp`** | The MCP server for AI agents |
| **`skills/diagram-author`** | The skill with the workflow and the AWS and Azure patterns |
| **`site-demo`** | An Astro site that hosts the playground |

## Icons

Lucide icons (more than 2,400) are included. I do not distribute Azure and AWS icons: each user downloads the packages from the official sites and imports them with `dgm icons update`. I did not want to redistribute third-party assets, and the project was designed that way from the start.

## Ready to be assisted by AI

The MCP server exposes tools such as `dgm_search_icons`, `dgm_validate_diagram`, and `dgm_render_diagram`. The assistant consults the guide, searches for icons (without making them up), writes the specification, validates it, renders a PNG, looks at it, fixes it, and saves it.

That last step, looking at the result, is the one that matters. A model that writes YAML blindly makes layout mistakes it cannot see. With the PNG in front of it, it can correct them. There is also an OpenCode agent (`diagram-specialist`) that encapsulates the whole process and accepts text, project files, or a reference image, such as a screenshot of the portal or a hand-drawn sketch.

## Security

When an assistant writes files, what it writes must be handled with care. The project has an explicit security model: theme values are validated before they go into the SVG, icons pass through an allowlist that blocks scripts and external links, and the MCP server only writes inside the project root without overwriting existing files. The interactive SVG includes a small script, so if you serve it on your own website, do it from your own origin, or use `--static` if you need a file without scripts.
